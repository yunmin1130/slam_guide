## 개념

이번 주를 마치면 11주차에 TS로 만든 미니 VO를 C++로 옮겨, 같은 TUM 시퀀스에서 같은 방식으로 채점한 결과를 보여 줄 수 있다. 채용 공고의 "C++, Eigen, OpenCV, CMake, CI" 줄을 저장소 하나로 증명하는 주차다.

### 왜 C++로 다시 짜나

SLAM 현업 코드(ORB-SLAM3, VINS-Fusion, FAST-LIO)는 거의 다 C++이다. 면접에서는 알고리즘 설명과 함께 "그걸 C++로 짜 봤나"를 묻는다. TS 버전은 원리를 손으로 익히는 용도였고, C++ 버전은 실무 도구로 같은 일을 하는 용도다.

이번에는 수학을 다시 손코딩하지 않는다. 특징점 추적, E 추정, PnP, 삼각측량은 OpenCV API를 쓴다. 11주차에서 직접 짠 함수가 각 API 안에서 무엇을 하는지 알고 있으니, 인자와 결과를 바르게 다루는 데 집중한다.

### 이번 주 산출물

| 산출물 | 확인 방법 |
| --- | --- |
| C++ 단안 VO | 추적 프레임과 끊긴 지점 기록 |
| evo 채점 | ATE·RPE (`-as`) |
| GTest | `ctest` 통과 |
| CI | GitHub Actions 초록불 |
| 결과 JSON | 이 페이지 쇼케이스 표 |

이 레슨에는 local BA가 없다. 11d 표처럼 BA 없이는 fr1/xyz가 150프레임 안팎에서 끊길 수 있고, 그래도 이 레슨은 끝난다. 끊긴 지점까지의 궤적으로 evo·쇼케이스를 진행하고, 끝까지 잇는 일은 12b(Ceres local BA)에서 한다.

정답 VO 코드는 주지 않는다. 이 저장소가 포트폴리오이기 때문이다. 레슨은 폴더 구조, 빌드 설정, API 이름, 단계별 힌트까지만 준다.

### WSL2 규칙

WSL2(Windows Subsystem for Linux 2)는 Windows 안에서 진짜 리눅스 커널을 돌린다. Ubuntu 24.04를 쓰면 필요한 라이브러리가 apt 한 줄로 깔린다. 지켜야 할 규칙이 네 개 있다.

1. **코드와 데이터는 리눅스 홈(`~/`)에 둔다.** WSL 안의 홈은 리눅스 파일 시스템(ext4)이다. `/mnt/c`(Windows 디스크)에서 빌드하거나 사진을 읽으면 몇 배 느리다.
2. **메모리 상한을 정한다.** Windows 사용자 폴더의 `.wslconfig`에 메모리 8GB 이상과 swap을 적는다. 상한이 너무 작으면 C++ 빌드가 메모리 부족으로 멈춘다.
3. **에디터는 VS Code Remote-WSL로 연다.** WSL 터미널에서 `code .`를 치면 Windows의 VS Code가 WSL 안의 폴더를 연다. 확장(C/C++, CMake Tools)은 WSL 쪽에 설치된다.
4. **Docker는 하나만 쓴다.** Docker Desktop(WSL2 백엔드)을 쓰거나 WSL 안에 Docker 엔진을 깔거나, 둘 중 하나다. 둘을 같이 쓰면 소켓이 꼬인다.

환경 세팅 상한은 1단위(약 5시간)다. 넘기면 붙잡고 있지 말고 개발 컨테이너(devcontainer: 개발 환경 전체를 Docker 이미지로 고정한 것. VS Code "Dev Containers" 확장, `ubuntu:24.04` 이미지에 같은 apt 패키지)로 옮긴다.

## 실습: 환경 세팅

### WSL2 Ubuntu 24.04 설치

Windows PowerShell을 관리자 권한으로 열고 설치한다. 끝나면 재부팅하고 사용자 이름·비밀번호를 정한다.

```text
wsl --install -d Ubuntu-24.04
wsl -l -v
```

`wsl -l -v`의 VERSION 열이 2인지 확인한다. 1이면 이렇게 바꾼다.

```text
wsl --set-version Ubuntu-24.04 2
```

메모리 설정은 Windows 사용자 폴더(예: `C:\Users\나`)에 `.wslconfig` 파일을 만들어 적는다. 저장한 뒤 PowerShell에서 `wsl --shutdown`을 하고 다시 들어가야 적용된다.

```text
[wsl2]
memory=8GB
swap=8GB
```

PC 메모리가 16GB면 8GB, 32GB면 12~16GB가 적당하다. WSL 안에서 `free -h`로 적용됐는지 본다.

<SessionBreak id="s3" />

### apt 패키지와 버전 확인

WSL 터미널에서 설치한다. 줄 끝의 `\`는 "다음 줄에 이어진다"는 뜻이라 그대로 붙여 넣으면 된다.

```bash
sudo apt update
sudo apt install -y \
  build-essential cmake ninja-build \
  ccache git pkg-config \
  libopencv-dev libeigen3-dev \
  libceres-dev libgtest-dev \
  pipx
```

Ninja는 make보다 빠른 빌드 실행기이고, ccache는 한 번 컴파일한 결과를 저장해 두었다가 같은 파일을 다시 컴파일할 때 재사용하는 도구다.

Ubuntu 24.04 기준으로 OpenCV 4.6, Eigen 3.4, Ceres 2.2가 깔린다. 저장소 버전은 바뀔 수 있으니 **설치 후 직접 확인**하고 리포트에 적는다.

```bash
pkg-config --modversion opencv4
dpkg -s libeigen3-dev | grep Version
dpkg -s libceres-dev | grep Version
cmake --version
```

evo는 11d에서 Windows에 깔았더라도 WSL 쪽에 다시 깐다. Ubuntu 24.04의 Python 3.12는 시스템 패키지가 깨지지 않게 시스템 전체에 `pip install`을 막는다(PEP 668 규칙). 그래서 도구마다 따로 가상환경을 만들어 주는 pipx를 쓴다.

```bash
pipx ensurepath
pipx install evo
```

`pipx ensurepath` 뒤에는 터미널을 닫고 새로 열어야 `evo_ape` 명령이 잡힌다. Ubuntu에는 `python` 명령이 없고 `python3`만 있다는 점도 기억해 둔다.

### VS Code 연결

Windows의 VS Code에 "WSL" 확장을 깐다. WSL 터미널에서 작업 폴더로 가서 `code .`를 치면 왼쪽 아래에 "WSL: Ubuntu-24.04"가 뜬다. C/C++, CMake Tools 확장을 그 창에서 다시 설치한다.

```bash
mkdir -p ~/data
```

저장소도 WSL 홈에 새로 클론한다. Windows 쪽 클론을 `/mnt/c`로 열어 빌드하면 느리고, 줄 끝 문자(CRLF)가 섞여 스크립트가 깨질 수 있다. 주소는 내 GitHub 저장소 주소로 바꾼다.

```bash
cd ~
git clone \
  https://github.com/나/slam_guide.git
```

### OpenCV 첫 빌드

본격적으로 짜기 전에 "사진 한 장 읽고 크기 출력"만 하는 프로그램을 CMake로 빌드해 본다. 이게 되면 컴파일러, CMake, OpenCV 연결이 모두 된 것이다. 저장소와 섞이지 않게 홈에 연습 폴더를 따로 만든다.

```text
~/hello_cv/
  CMakeLists.txt
  main.cpp
```

`CMakeLists.txt`는 다섯 줄이면 된다.

```text
cmake_minimum_required(VERSION 3.22)
project(hello_cv CXX)
find_package(OpenCV REQUIRED)
add_executable(hello main.cpp)
target_link_libraries(hello
  ${OpenCV_LIBS})
```

- `main.cpp`에서 `cv::imread`로 `rgb/` 폴더의 사진 하나를 읽는다(`#include <opencv2/opencv.hpp>`).
- `img.cols`, `img.rows`를 출력한다. TUM은 640×480이다.
- 빌드와 실행은 아래와 같다. `rgb/` 안의 파일 이름 하나를 골라 넣는다.

```bash
cd ~/hello_cv
cmake -S . -B build
cmake --build build
D=~/data/rgbd_dataset_freiburg1_xyz
./build/hello "$D/rgb/파일.png"
```

### TS 함수 → OpenCV API 대응표

11주차에 직접 짠 것과 이번에 부를 API를 짝지어 둔다. 인자와 좌표 규약이 다른 곳이 함정이다.

| 이전 주차 (TS) | C++ (OpenCV) |
| --- | --- |
| KLT 추적 (10주차, `tum_tracks.py`) | `goodFeaturesToTrack`, `calcOpticalFlowPyrLK` |
| 왜곡 펴기 (4주차) | `undistortPoints` (`P = K`) |
| `initMap`의 E + 분해 | `findEssentialMat`, `recoverPose` |
| `triangulate` | `triangulatePoints` |
| `trackPnP` | `solvePnPRansac` |
| `refinePose` | `solvePnPRefineLM` |
| `localBA` | 12b (Ceres) |
| `ate`, `alignUmeyama` | 직접 (Eigen SVD) |

`undistortPoints`의 마지막 인자 `P`는 출력 투영 행렬이다. `P = K`를 주면 왜곡을 편 **픽셀** 좌표를 돌려주고, 주지 않으면 정규화 좌표(초점거리 1)를 돌려준다.

좌표 규약 세 가지를 확인해 둔다.

- `recoverPose`가 주는 `R`, `t`는 $x_2 = R x_1 + t$인 $T_{21}$이다. 11a `initMap`의 `T`와 같고, $\lVert t \rVert = 1$이다.
- `solvePnPRansac`이 주는 `rvec`, `tvec`은 월드 점을 카메라로 옮기는 $T_{cw}$다(`rvec`은 회전 벡터, `cv::Rodrigues`로 행렬). 11b `trackPnP`의 `T`와 같다.
- TUM 궤적 파일과 evo는 $T_{wc}$(카메라 → 월드)를 원한다. 출력할 때 $R_{wc} = R^\top$, $t_{wc} = -R^\top t$로 뒤집는다.

<LABox term="쿼터니언 저장 순서">
  **정의:** 같은 쿼터니언 $q = w + xi + yj + zk$를 라이브러리와 파일 형식마다 다른 순서로 적는다. 숫자 넷이 같아도 순서를 잘못 읽으면 전혀 다른 회전이 된다.

  **어디서 갈리나:** TUM `groundtruth.txt`와 evo의 TUM 형식은 `tx ty tz qx qy qz qw`(w가 마지막)다. 우리 트랙 JSON의 정답 자세는 `[tx, ty, tz, qw, qx, qy, qz]`(w가 먼저, 11d)였다. Eigen의 `Quaterniond(w, x, y, z)` 생성자는 w가 먼저인데, 메모리(`coeffs()`)에는 `x, y, z, w` 순서로 들어 있다.

  **확인 방법:** 정답 자세 하나를 읽어 회전 행렬로 바꾼 뒤 행렬식이 1이고 $R^\top R = I$인지 보는 것으로는 부족하다(순서가 틀려도 단위 쿼터니언이면 회전 행렬이 나온다). 카메라가 거의 안 움직이는 첫 몇 프레임에서 정답 회전이 단위에 가까운지, 출력 궤적을 evo에 넣었을 때 회전 RPE(아래 evo 절의 `-r angle_deg`)가 몇 도 안쪽인지로 확인한다.

  **이전 레슨:** [3a 쿼터니언](../w03-rotation-se3/), [11d 트랙 파일 형식](../w11d-evaluation-tum/)
</LABox>

## 실습: C++ VO 포팅

### 폴더 구조와 CMakeLists

저장소 루트에 `cpp/` 폴더를 만든다. 사이트(`site/`)와 섞이지 않게 C++ 코드는 전부 이 안에 둔다.

```text
cpp/
  CMakeLists.txt
  include/vo/   헤더
  src/          VO 라이브러리, 실행 파일
  tests/        GTest
```

CMakeLists 뼈대다. 파일 이름은 자유롭게 바꾼다. **아직 실행해 보지 않은 템플릿이다(검증 안 됨).** 처음 빌드에서 오류가 나면 메시지대로 고치고, 고친 내용을 노트에 남긴다.

```text
cmake_minimum_required(VERSION 3.22)
project(mini_vo CXX)
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

find_package(OpenCV REQUIRED)
find_package(Eigen3 3.3 REQUIRED
  NO_MODULE)

add_library(vo
  src/tum.cpp src/tracker.cpp
  src/vo.cpp src/eval.cpp)
target_include_directories(vo
  PUBLIC include)
target_link_libraries(vo PUBLIC
  ${OpenCV_LIBS} Eigen3::Eigen)

add_executable(run_tum
  src/run_tum.cpp)
target_link_libraries(run_tum
  PRIVATE vo)

enable_testing()
find_package(GTest REQUIRED)
add_executable(vo_tests
  tests/eval_test.cpp)
target_link_libraries(vo_tests
  PRIVATE vo GTest::gtest_main)
include(GoogleTest)
gtest_discover_tests(vo_tests)
```

CMake는 적힌 소스 파일이 하나라도 없으면 설정 단계에서 멈춘다. 그래서 이 세션에서는 위 파일 여섯 개를 **빈 껍데기**로 먼저 만든다.

- `src/run_tum.cpp`: `int main() { return 0; }` 한 줄.
- `tests/eval_test.cpp`: `#include <gtest/gtest.h>`와 `TEST(Smoke, Runs) { SUCCEED(); }`.
- 나머지 `src/*.cpp`: 비워 둔다(빈 파일도 컴파일된다).

빌드는 Ninja로 한다. 처음 한 번만 `-S`·`-B`로 설정하고, 그다음은 `--build`만 반복한다. 이 세션의 목표는 빈 프로그램이 빌드되고 `ctest`가 통과하는 것까지다. 데이터로 돌리는 것은 다음 세션부터다.

```bash
cmake -S cpp -B build -G Ninja \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build
```

### 추적 수 비교

같은 시퀀스로 `tum_tracks.py`가 만든 JSON의 프레임별 특징점 수와 내 C++ 추적기의 수를 나란히 찍어 본다. JSON은 11d에서 만든 파일(Windows 쪽 저장소의 `datasets/tracks/`)이고, 프레임 $i$의 점 수는 `frames[i].features`의 길이다. WSL에서는 `/mnt/c/…` 경로로 바로 읽거나 `cp`로 홈에 복사한다. 처음 몇 프레임이 300개 안팎이고, 이후 보충 직전에 210개 아래로 내려갔다 다시 올라오면 된다.

- 수가 훨씬 적으면 앞뒤 검사 임계값이나 창 크기를 확인한다.
- 수가 계속 300에 붙어 있으면 보충을 매 프레임 하고 있는 것이다. 그러면 id가 너무 빨리 바뀌어 PnP에 쓸 오래된 점이 모자란다.
- 왜곡 펴기를 빼먹으면 fr1에서 가장자리 점의 위치가 수 픽셀 틀어진다. 초기화는 되지만 ATE가 눈에 띄게 나빠진다.

### 초기화

11a와 같다. 첫 프레임과 시차가 충분한 프레임 사이에서 E를 구하고 자세를 복원한다.

<Hint level={1}>
  두 프레임의 같은 id 점(왜곡을 편 픽셀 좌표)으로 `cv::findEssentialMat`(`cv::RANSAC`, 신뢰도 0.999, 임계값 약 1&nbsp;px)을 부르고, 그 마스크와 함께 `cv::recoverPose`를 부른다. `recoverPose`가 돌려주는 정수는 카메라 앞에 놓인 inlier 수다.
</Hint>

<Hint level={2}>
  11a처럼 시차를 검사한다. 시차각 중앙값이 3°(TS 실행기의 TUM 설정) 아래거나 살아남은 점이 50개 아래면 초기화를 미루고 기준 프레임과 다음 프레임으로 다시 시도한다. 공통 점이 너무 줄면 기준 프레임을 앞으로 옮긴다(11주차 `findInit`).
</Hint>

<SessionBreak id="s11" />

### 초기화 디버그

- `recoverPose`의 inlier가 수십 개뿐이면 좌표와 `K`가 어긋난 것이다. 두 경우를 나눠 확인한다.
  - 픽셀 좌표(`undistortPoints`에 `P = K`)를 넣었다면 `findEssentialMat`과 `recoverPose`에 `K`를 넘긴다.
  - 정규화 좌표(`undistortPoints`를 `P` 없이)를 넣었다면 `K` 대신 단위 행렬(초점거리 1, 주점 0)을 넘긴다. 이때 RANSAC 임계값도 픽셀이 아니라 정규화 단위(약 1/초점거리)로 바꾼다.
- 첫 키프레임을 월드 원점으로 두고, 두 번째 키프레임의 `t` 길이 1이 이 VO의 길이 단위가 된다. 이후 evo `-as`의 `s`(크기 맞춤)가 이 단위를 미터로 맞춘다.
- TS 실행기에서 같은 시퀀스의 초기화 프레임 번호를 보고 비슷한지 견줘 본다(fr1/xyz는 처음 몇 프레임 안).

### 삼각측량과 맵 포인트

<Hint level={1}>
  `cv::triangulatePoints`는 두 카메라의 3×4 투영 행렬과 2×N 점을 받아 4×N 동차 좌표를 돌려준다. 네 번째 성분으로 나눠 3D 점을 얻는다. 투영 행렬은 `K·[R|t]`(픽셀 좌표를 넣을 때) 또는 `[R|t]`(정규화 좌표를 넣을 때) 중 하나로 일관되게 쓴다.
</Hint>

<Hint level={2}>
  11a와 같은 거르기를 한다. 두 카메라 앞($z > 0$)에 있고, 두 재투영 오차가 임계값 안이고, 시차각이 충분한 점만 맵 포인트로 남긴다. 숫자는 TS 실행기의 TUM 설정(`site/src/lib/voJob.ts`)과 같게 둔다: 재투영 임계값 2&nbsp;px, 시차각 3°. 맵 포인트는 특징점 id를 그대로 키로 쓴다(`std::unordered_map`, 키 `int`, 값 `Eigen::Vector3d`).
</Hint>

### PnP 추적

<Hint level={1}>
  지금 프레임의 특징점 중 맵에 있는 id만 골라 3D–2D 짝을 만들고 `cv::solvePnPRansac`을 부른다. 재투영 임계값은 11d의 TUM 설정(6&nbsp;px)에서 시작한다. 직전 프레임 자세를 `rvec`, `tvec` 초기값으로 주고 `useExtrinsicGuess = true`로 하면 안정적이다.
</Hint>

<Hint level={2}>
  inlier만 모아 `cv::solvePnPRefineLM`으로 다듬는다. 11b `refinePose`가 하던 일이다(자세만 바꾸는 LM). OpenCV 4.1 이후에 들어간 함수로 알고 있지만 검증하지 않았으니, 설치한 버전의 헤더(`calib3d.hpp`)에 있는지 확인한다.
</Hint>

### PnP 디버그와 실패 처리

- inlier 수가 기준(11b `minInliers`, TS 실행기의 TUM 설정은 30) 아래로 떨어지면 추적 실패로 보고 그 프레임 번호를 기록한 뒤 멈춘다. 재위치 인식은 이번 범위가 아니다(11d의 fr1/desk 실패와 같은 한계).
- PnP의 outlier였던 맵 포인트는 지우고 그 id를 다시 쓰지 않는다. 11c에서 읽은 `vo` 조립 코드(`core/reference/w11.ts`의 `cullOutliers`)가 지운 id를 `banned` 집합에 넣어 두고 새 점을 만들 때 건너뛰는 부분이다. 이걸 빼면 fr3/long_office에서 일찍 끊긴다.
- `cv::Mat`과 Eigen 사이는 `opencv2/core/eigen.hpp`의 `cv::cv2eigen`, `cv::eigen2cv`로 옮긴다. 이 헤더는 Eigen 헤더 다음에 include해야 컴파일된다.

### 키프레임과 새 점

11c `selectKeyframe` 규칙을 그대로 옮긴다. 지난 키프레임 뒤로 최소 2프레임이 지났고, 추적 inlier가 지난 키프레임의 0.8배 아래로 떨어지면 새 키프레임을 만든다. 8프레임이 지나면 무조건 만든다. TS 실행기의 TUM 설정(`site/src/lib/voJob.ts`)과 같은 값이다.

새 키프레임에서는 맵에 아직 없는 id를 그 점을 처음 본 프레임과 삼각측량해 맵에 더한다(11c `newPoints`). local BA는 12b에서 Ceres로 붙인다. 이 레슨에서는 BA 없이 어디까지 가는지 기록하는 것이 목표다.

<Details summary="(선택) Eigen으로 local BA 옮기기">
  11d 표에서 local BA를 끄면 fr1/xyz는 151, fr3은 92프레임에서 끊겼다. C++도 BA 없이는 비슷하게 끊길 수 있다. 12b(Ceres)로 바로 가는 것이 정석이다.

  12b를 미루고 싶으면 8b `smallBA`의 가우스-뉴턴 구조(재투영 잔차, `projectionJacobian`, 정규방정식)를 Eigen으로 옮기는 방법도 있다. 창이 작으면(키프레임 5개, 점 수백 개) 밀집 행렬 `Eigen::LDLT`로 풀어도 충분하다.
</Details>

### TUM 형식 궤적 출력

evo가 읽는 TUM 형식은 한 줄에 여덟 숫자다. w가 마지막이다(LA 박스).

```text
시각 tx ty tz qx qy qz qw
```

<Hint level={1}>
  자세 $T_{cw}$를 $T_{wc}$로 뒤집고, `Eigen::Quaterniond q(R_wc)`로 쿼터니언을 만든다. `q.x() q.y() q.z() q.w()` 순서로 쓴다. 추적에 실패해 자세가 없는 프레임은 줄을 쓰지 않는다(evo가 시각으로 짝짓는다).
</Hint>

### fr1/xyz 돌리고 끊긴 지점 기록

이 세션의 완료 기준은 "끝까지"가 아니라 "어디까지 갔는지 기록"이다. BA가 없으니 TS 실행기의 BA 끔 결과(fr1/xyz 151, fr3 92프레임)와 비슷한 곳에서 끊기면 정상이다. 추적한 프레임 수, 끊긴 프레임 번호, 실행 시간(`std::chrono::steady_clock`)을 노트에 적는다.

- 실행 시간은 TS 실행기(PC 브라우저)보다 몇 배 빨라야 정상이다.
- 끝까지 잇는 일은 12b(Ceres local BA)나 위 선택 접기(Eigen local BA)에서 한다. 그 전에도 끊긴 지점까지의 궤적으로 아래 evo·쇼케이스를 진행할 수 있다.
- 몇십 프레임 만에 끊기면 BA 탓이 아니다. inlier 수를 프레임마다 찍어 어디서 떨어지는지 본다. 대개 새 점 추가(삼각측량 기준 프레임)나 맵 정리가 빠졌다.
- 궤적이 거울에 비친 것처럼 뒤집혀 보이면 $T_{cw}$를 뒤집지 않고 그대로 출력했거나, 쿼터니언 순서가 틀렸다.

### 우메야마·ATE를 GTest로

11d `alignUmeyama`, `ate`를 C++로 옮긴다. 이것만은 OpenCV가 아니라 Eigen으로 직접 짠다(`Eigen::JacobiSVD`). 테스트도 TS 테스트(`core/tests/w11.test.ts`)의 해당 케이스를 옮긴다.

- 기본: 알려진 $s, R, t$로 옮긴 점을 정확히 되찾는다.
- 경계: 점 3개 미만, 한 직선 위의 점이면 예외(`EXPECT_THROW`).
- 경계: 반사 경우($\det U \det V < 0$)에도 회전이 나온다(TS 테스트와 같은 분류).
- 수치: 잡음을 섞은 무작위 점에서 ATE가 잡음 크기 정도로 나온다.

```text
TEST(Umeyama, RecoversSim3) {
  // 알려진 s, R, t로 점을 옮긴다
  // 내 함수로 되찾는다
  EXPECT_NEAR(s_est, s, 1e-9);
}
```

### GTest 디버그, Eigen::umeyama와 대조

Eigen에는 같은 일을 하는 `Eigen::umeyama(src, dst, true)`가 이미 있다(4×4 동차 행렬을 돌려준다). 내 함수 대신 쓰지는 않고, 테스트에서 **두 결과가 같은지** 대조하는 기준으로 쓴다. 이렇게 하면 "내가 이해한 식"과 "라이브러리 구현"을 동시에 검증한다.

- `src`, `dst`는 3×N 행렬(열마다 점)이다. TS처럼 점 배열을 그대로 넣으면 모양이 맞지 않는다.
- 실패한 테스트의 출력까지 보려면 `ctest`에 `--test-dir build`와 `--output-on-failure`를 준다.

### evo로 채점

11d와 같은 명령에 회전 RPE(`-r angle_deg`)를 하나 더한다. `--save_results`로 결과를 zip으로 저장해 두면 쇼케이스 JSON을 만들 때 다시 쓴다. 추적이 중간에 끊겼으면 그때까지의 궤적만 들어 있고, evo는 있는 시각만 짝지어 잰다.

```bash
evo_ape tum groundtruth.txt est.txt \
  -as --t_max_diff 0.02 \
  --save_results ape.zip
evo_rpe tum groundtruth.txt est.txt \
  -as -d 15 -u f \
  --save_results rpe.zip
evo_rpe tum groundtruth.txt est.txt \
  -as -d 15 -u f -r angle_deg \
  --save_results rpe_rot.zip
```

fr3/long_office(10Hz)는 `-d 10`으로 한다. 같은 이름의 zip이 이미 있으면 evo가 덮어쓸지 묻는다. 시퀀스마다 폴더를 나눠 두면 헷갈리지 않는다.

TS(mine) 실행기의 궤적 파일도 같은 명령으로 잰다. 브라우저가 Windows의 다운로드 폴더에 저장했으니 먼저 WSL로 복사한다.

```bash
cd /mnt/c/Users/나/Downloads
cp tum-…-vo.txt ~/ts.txt
```

그래야 세 숫자(TS 사이트, TS evo, C++ evo)를 같은 표에 올릴 수 있다.

| 확인 | 기대 |
| --- | --- |
| C++ 추적 프레임 | TS와 비슷하거나 많음 |
| ATE (`-as`) | TS와 같은 자릿수 |
| 실행 시간 | TS보다 몇 배 빠름 |

숫자가 TS와 크게 다르면 프레임 간격, 특징점 상수, 추적 임계값이 같은지부터 본다. 알고리즘이 같아도 OpenCV의 RANSAC 난수와 EPnP 같은 내부 방법이 달라 조금씩은 다르다.

### 결과 쇼케이스

결과를 사이트에 올린다. 아래 스크립트가 evo zip에서 숫자(RMSE)를 꺼내 JSON을 만든다. 궤적 자체는 넣지 않는다. git 커밋 해시는 스크립트가 자동으로 넣고, 저장 폴더(`site/src/data/cpp-results/`)가 없으면 만든다. 저장소 루트에서 실행한다.

```bash
python3 datasets/cpp_result.py \
  --sequence fr1/xyz --impl cpp \
  --ape ape.zip --rpe rpe.zip \
  --rpe-rot rpe_rot.zip \
  --tracked 151 --total 300
```

`--impl`은 `cpp`, `ts-mine`, `ts-reference`, `orbslam3` 중 하나다. `--tracked`, `--total`에는 실행 파일이 출력한 추적 프레임 수와 전체 프레임 수를 넣는다(위 숫자는 BA 없이 끊긴 경우의 예). 파일 이름은 `<시퀀스>-<구현>.json`으로 정해지고, 같은 이름이 있으면 멈춘다. 다시 만들 때는 `--force`를 준다.

TS 숫자는 두 가지로 올린다.

- **TS 사이트 숫자:** 실행기 화면의 ATE·RPE를 직접 넣는다(미터 단위).

  ```bash
  python3 datasets/cpp_result.py \
    --sequence fr1/xyz --impl ts-mine \
    --ate-rmse 0.046 --rpe-trans 0.012
  ```

- **TS를 evo로 잰 숫자:** zip으로 넣고 `--note "evo"`로 구분한다. 같은 시퀀스·구현이라 파일 이름이 겹치니 `--out`으로 이름을 바꾼다(`--out`의 폴더는 미리 있어야 한다).

  ```bash
  python3 datasets/cpp_result.py \
    --sequence fr1/xyz --impl ts-mine \
    --ape ts_ape.zip --rpe ts_rpe.zip \
    --note "evo" \
    --out site/src/data/cpp-results/x.json
  ```

  `x.json`은 `fr1-xyz-ts-mine-evo.json`처럼 알아보기 쉬운 이름으로 바꿔 쓴다.

시퀀스마다 이렇게 만들면 아래 표가 TS·C++·evo를 한 줄씩 나란히 보여 준다. JSON을 커밋하고 푸시하면 배포 뒤 이 자리에 나타난다.

### CI: cpp.yml

C++ 빌드와 테스트는 사이트 배포와 따로 돈다. `cpp/` 아래가 바뀔 때만 돌게 한다. 데이터셋은 CI에서 받지 않는다(용량, 라이선스). 그래서 CI에서는 합성 데이터 GTest만 돈다.

**아직 실행해 보지 않은 템플릿이다(검증 안 됨).** 특히 apt만으로 `GTest::gtest_main` 타깃을 찾는지, ccache 액션이 그대로 동작하는지는 첫 실행에서 확인한다. ccache는 CMake가 읽는 환경 변수 `CMAKE_CXX_COMPILER_LAUNCHER`로 붙인다.

```text
name: cpp
on:
  push:
    paths:
      - "cpp/**"
      - ".github/workflows/cpp.yml"
  pull_request:
    paths: ["cpp/**"]
jobs:
  build:
    runs-on: ubuntu-24.04
    env:
      CMAKE_CXX_COMPILER_LAUNCHER: ccache
    steps:
      - uses: actions/checkout@v4
      - name: deps
        run: |
          sudo apt-get update
          sudo apt-get install -y \
            cmake ninja-build ccache \
            libopencv-dev \
            libeigen3-dev \
            libceres-dev libgtest-dev
      - uses: hendrikmuhs/ccache-action@v1
      - name: build
        run: |
          cmake -S cpp -B build -G Ninja \
            -DCMAKE_BUILD_TYPE=Release
          cmake --build build
      - name: test
        run: |
          ctest --test-dir build \
            --output-on-failure
```

액션 버전 태그(`@v4`, `@v1`)는 쓸 때 각 저장소에서 최신 태그를 확인한다. 사이트 배포 워크플로(`deploy.yml`)는 main 푸시의 `paths-ignore`에 이미 `cpp/**`가 있어서, C++만 바꿨을 때 사이트를 다시 배포하지 않는다.

<CheckQuestion q="solvePnPRansac이 돌려주는 rvec, tvec은 어떤 변환이고, TUM 궤적 파일에는 무엇을 어떤 순서로 써야 하나?" kind="개념">
  `rvec`(회전 벡터)과 `tvec`은 월드 점을 카메라 좌표로 옮기는 $T_{cw}$다: $p_c = R X_w + t$. TUM 궤적 파일과 evo는 카메라 자세를 월드에서 본 $T_{wc}$를 원하므로 $R_{wc} = R^\top$, $t_{wc} = -R^\top t$로 뒤집는다.

  한 줄에 `시각 tx ty tz qx qy qz qw` 순서로 쓴다. 쿼터니언의 w가 마지막이라, Eigen 생성자(w가 먼저)나 우리 트랙 JSON(w가 먼저)과 헷갈리지 않게 한다.
</CheckQuestion>

<CheckQuestion q="같은 알고리즘을 옮겼는데 C++ VO의 ATE가 TS 버전과 다르게 나왔다. 왜 그럴 수 있나?" kind="왜">
  RANSAC은 난수를 쓰므로 실행마다, 구현마다 고르는 표본이 다르다. OpenCV의 `solvePnPRansac`은 최소 표본에서 DLT가 아닌 다른 방법(EPnP 등)을 쓰고, `findEssentialMat`은 8점이 아니라 5점 알고리즘을 쓴다. 다듬기(LM)의 멈춤 기준도 다르다.

  또 특징점 상수, 왜곡 펴기, 프레임 간격, 추적 임계값 중 하나라도 다르면 궤적이 달라진다. 단안 VO는 작은 차이가 스케일 드리프트로 쌓이므로, 같은 자릿수면 정상이고 몇 배 차이면 설정부터 맞춰 본다.
</CheckQuestion>

<CheckQuestion q="CI에서 TUM 데이터셋 없이 VO 코드를 어떻게 테스트하나?" kind="실무">
  데이터셋은 용량과 라이선스 때문에 CI에서 받지 않는다. 대신 정답을 아는 합성 데이터로 단위 테스트를 만든다. 예를 들어 알려진 Sim(3)로 옮긴 점으로 우메야마를, 알려진 자세에서 투영한 점으로 PnP·삼각측량 래퍼를 검사한다.

  실데이터 결과(ATE)는 로컬에서 evo로 재서 결과 JSON으로 커밋한다. 이렇게 하면 CI는 빠르고 결정적(같은 입력이면 같은 결과)이며, 실데이터 회귀는 결과 JSON의 숫자 변화로 본다.
</CheckQuestion>
